## 1. RAGAS 当前版本 API(0.4.3)

⚠️ **重大漂移:RAGAS 0.4 存在"两套并存 API",老教程几乎全是被弃的老路。**

| 轨道 | import 前缀 | 状态【文档】 |
|---|---|---|
| **A. 经典 legacy** | `ragas.metrics` + `evaluate()` + `EvaluationDataset` + `LangchainLLMWrapper`/`LangchainEmbeddingsWrapper` | **0.4 起标 deprecated,1.0 移除**(仍可跑,有告警) |
| **B. collections / native** | `ragas.metrics.collections` + `llm_factory` + native `OpenAIEmbeddings`/`embedding_factory` | **未来主线**,不弃 |

### ① 四大核心指标:import 路径 + 是否需要 reference【文档】

| 指标 | legacy import(`ragas.metrics`) | collections import(`ragas.metrics.collections`) | 需 reference? | 需 embeddings? | SingleTurnSample 字段 |
|---|---|---|---|---|---|
| **faithfulness** | `Faithfulness` | `Faithfulness` | **否** | 否 | user_input, response, retrieved_contexts |
| **answer relevancy** | `ResponseRelevancy` | `AnswerRelevancy` | **否** | **是** | user_input, response, retrieved_contexts |
| **context precision** | `LLMContextPrecisionWithReference` | `ContextPrecision` | **是** | 否 | user_input, **reference**, retrieved_contexts |
| context precision(无ref变体) | `LLMContextPrecisionWithoutReference` | `ContextUtilization` | 否 | 否 | user_input, response, retrieved_contexts |
| **context recall** | `LLMContextRecall` | `ContextRecall` | **是** | 否 | user_input, response, **reference**, retrieved_contexts |

语义:faithfulness=回答是否忠于检索到的上下文(反臆造);answer_relevancy=回答与问题相关度(LLM 反推问题 + embedding 余弦);context_precision=检索到的块里"有用块是否排在前面";context_recall=参考答案的信息是否都被检索到的上下文覆盖。

**弃答/通用回答模式的坑**【文档】:`context_precision` 无 ground truth 会走 `context_utilization`(用 response 代替 reference),官方提示"无 ref 的 context_precision 将弃用,改用 context_utilization"。

### ② 构造评测数据【文档】
现行是 `SingleTurnSample` + `EvaluationDataset`(**不是**旧的裸 dict / HF `datasets.Dataset`;`from_dict`/HF 路径仍在但非推荐):
```python
from ragas import EvaluationDataset, SingleTurnSample
# 单条
s = SingleTurnSample(
    user_input="NCCL 的作用?",
    response="<pipeline 生成的答案>",
    retrieved_contexts=["<检索到的块文本>", ...],
    reference="<黄金答案,仅 recall/precision 用>",
)
# 批量:最省事——一个 list[dict] 直接喂
ds = EvaluationDataset.from_list([
    {"user_input": "...", "response": "...", "retrieved_contexts": [...], "reference": "..."},
    ...
])
```

### ③ 喂自定义评判官 LLM + 自定义 embeddings —— 我们的 GLM-5.2 / 百炼 v4

我们有**两个不同端点**:判官 LLM=GLM-5.2@MaaS(`llm_base_url`),embeddings=百炼 text-embedding-v4@dashscope-compat(`embedding_base_url`)。两条轨道都能接,给出两版:

**轨道 A(推荐 M3 起步,最快转绿、最容错):把 langchain 实例直接喂 `evaluate()`**
ragas 会自动用 `LangchainLLMWrapper`/`LangchainEmbeddingsWrapper` 包起来(也可手动包)。判官走 ragas 自带 prompt+文本解析,**不依赖模型的 function-calling**,对 GLM 更宽容。
```python
from langchain_openai import ChatOpenAI, OpenAIEmbeddings   # ragas 装好后可用
from ragas import evaluate, EvaluationDataset
from ragas.metrics import Faithfulness, ResponseRelevancy, \
    LLMContextPrecisionWithReference, LLMContextRecall
from blog_rag.config import settings

judge = ChatOpenAI(
    model=settings.llm_model, base_url=settings.llm_base_url,
    api_key=settings.require_api_key(), temperature=0,
    model_kwargs={"extra_body": {"enable_thinking": False}},  # 关思考,见 notes 教训
)
emb = OpenAIEmbeddings(
    model=settings.embedding_model, base_url=settings.embedding_base_url,
    api_key=settings.require_api_key(),
    chunk_size=settings.embedding_batch,        # 百炼 batch 上限=10(R2)
    check_embedding_ctx_length=False,           # 百炼必须(R2),否则 tiktoken 分片崩
)
result = evaluate(
    dataset=EvaluationDataset.from_list(rows),
    metrics=[Faithfulness(), ResponseRelevancy(),
             LLMContextPrecisionWithReference(), LLMContextRecall()],
    llm=judge, embeddings=emb,      # 传 langchain 实例,ragas 自动 wrap
)
df = result.to_pandas()            # 每条样本逐指标分数 → 存 CSV
```
> `evaluate()` 返回可 `.to_pandas()` 得**逐样本 + 聚合**分数(golden-set 评测正需要)。指标级 llm/embeddings 优先级高于 evaluate() 级,可给某指标单独换模型。

**轨道 B(未来主线,非弃用,但有实测风险):collections + native**
```python
import openai
from ragas.llms import llm_factory
from ragas.embeddings import OpenAIEmbeddings          # ragas 原生(非 langchain)
from ragas.metrics.collections import Faithfulness, AnswerRelevancy, ContextPrecision, ContextRecall

judge = llm_factory("glm-5.2",
    client=openai.OpenAI(base_url=settings.llm_base_url, api_key=key))
emb = OpenAIEmbeddings(                               # base_url 设在 client 上,不是参数
    client=openai.OpenAI(base_url=settings.embedding_base_url, api_key=key),
    model=settings.embedding_model)
scorer = Faithfulness(llm=judge)
await scorer.ascore(user_input=..., response=..., retrieved_contexts=[...])
```
⚠️ collections/`llm_factory` **底层用 `instructor` 做结构化输出**,依赖判官模型支持 function-calling / JSON-schema。GLM-5.2@MaaS 是否稳支持=**【推测,需实测】**。→ 故 M3 起步走轨道 A 更稳。

`LangchainLLMWrapper`/`LangchainEmbeddingsWrapper` 也可手动用,但**已标 deprecated**;直接把 langchain 实例喂 `evaluate()` 等效且更简。

### ④ ground truth 影响黄金集 schema
- **需要 reference 的**:context_precision(WithReference)、context_recall。
- **不需要 reference 的**:faithfulness、answer_relevancy。
→ 黄金集**每条都建议写 reference**(否则精度/召回两项无法算,只能退到 utilization/without-reference 变体,评测信息量减半)。详见 §5。

## 2. Langfuse

### ① 自托管 vs 云【文档】
开源,两种:
- **云**:有免费额度,注册即用,零运维。但 trace 里含 query+检索到的语料原文 → **数据出域**考量(与本项目"数据是否出域须拍板"的一贯红线一致)。
- **自托管**:v3/v4 的 OTel 架构较重,需 **Postgres + ClickHouse + Redis + S3(对象存储)** 一套 docker compose。单用户跑这套=显著运维负担。

### ② 最简接入【文档,注意版本漂移】
当前 SDK 是 **OTel 版**(PyPI 最新 **4.14.0**,`requires python>=3.10`)。**老教程的 `from langfuse.decorators import observe, langfuse_context` 已作废**,现行:
```python
from langfuse import observe, get_client
@observe()
def my_rag(q): ...
langfuse = get_client(); langfuse.flush()
```
两种集成模式:①在线 `@observe` 装饰管道函数自动建 trace;②离线批量:从 Langfuse 拉 trace → 构 `EvaluationDataset` → `ragas.evaluate` → 把分数 push 回 trace。

### ③ RAGAS ↔ Langfuse 现状【文档】
官方 cookbook 存在且近期更新(`langfuse.com/guides/cookbook/evaluation_of_rag_with_ragas`),但**注意漂移**:ragas 官方那篇 Langfuse 集成页 + 多数 GitHub 示例仍用 v2 老 import,只有 Langfuse 自家 cookbook 是 v3/v4 语法。接入时以 Langfuse 官方 cookbook 为准。

### ④ 单用户右尺寸建议 →【强烈建议 Langfuse 延后,M3 只用 RAGAS 出分】
理由:
1. **M3 目标=出分调参**,`ragas.evaluate().to_pandas()` 落 CSV/JSON 就完全满足(聚合+逐样本),**零基建**。
2. Langfuse 的价值是**在线追踪/时间序列监控 dashboard**——那是有真实用户流量后(本项目 **M6 对话UI+反馈闭环**)才有意义的东西,不是 M3 评分该背的包袱。
3. 自托管重(ClickHouse 全家桶)/ 云有数据出域顾虑,单用户两头都不划算。
→ **结论:M3 = RAGAS 本地出分;Langfuse 归入可选 `[obs]` extra,M6 有 UI trace 值得监控时再接**。与 §0 拆 extra 建议一致。

## 3. 检索指标 Hit@k / MRR ——【确认:自己算,不靠 RAGAS】

- RAGAS 的 context_precision/recall 是 **LLM 判"语义相关"**,**不是**按 doc_id 命中的排序指标。RAGAS **不提供** Hit@k / MRR / nDCG / Recall@k(经典排序检索指标)。
  - 边角:有 `NonLLMContextPrecisionWithReference`(需 `reference_contexts`,靠 rapidfuzz 文本相似)和 `IDBasedContextPrecision`(需 `reference_context_ids`),但**都不是 Hit@k/MRR**,别绕。
- → **Hit@k / MRR 自实现**,极简、无依赖,匹配键=项目 chunk metadata 已有的 **`doc_id`**(notes:确定性 chunk_id + 去重 by doc_id)。

### 最简实现要点
每条黄金问题标注 `relevant_doc_ids`(该问题答案应命中的**源文档 id** 集合)。跑 retriever 拿 top-k 的 `doc_id` 有序列表:
```python
def hit_at_k(ranked_doc_ids, relevant_ids, k):
    return 1.0 if set(ranked_doc_ids[:k]) & set(relevant_ids) else 0.0

def reciprocal_rank(ranked_doc_ids, relevant_ids):
    for i, d in enumerate(ranked_doc_ids, 1):
        if d in relevant_ids:
            return 1.0 / i
    return 0.0
# 全集平均:Hit@k = mean(hit_at_k(...)) ; MRR = mean(reciprocal_rank(...))
```
注意:去重后按 **doc 级**(非 chunk 级)比,与 rag_chain 的 `_dedupe_by_doc` 口径对齐;retriever 返回顺序=重排后顺序(评测检索端建议同时看"重排前 RRF 序"与"重排后序"两版,定位是召回问题还是排序问题)。

## 4. "GLM-5.2 当评判官"可行性

- **可行性:轨道 A(evaluate + langchain 实例)下大概率可行**【推测,需 M3 冒烟实测一条】。ragas 判官只需模型按提示返回可解析文本,GLM-5.2 OpenAI-兼容对话已在项目全程验证可用。
- **判官参数**:`temperature=0` + **关思考**(`extra_body={"enable_thinking": False}`,notes 实测判断类调用 5.5s→~1s 且结果不漂)。判官/打分本质是判断类调用,关思考正确。
- **韧性**:notes 记 MaaS 流式偶发 `WinError 10054` 断连;ragas 批量会并发多次调用判官 → **务必配重试**(ragas evaluate 有 `run_config`/max retries;或给 ChatOpenAI `.with_retry()`)。判官调用量 = 样本数 × 指标数 × 每指标内部调用(faithfulness 会拆句多调),**50 条黄金集可能是数百次判官调用** → 关思考省时省钱是刚需。
- **轨道 B 风险**:collections/instructor 需 GLM 支持 function-calling 结构化输出,未证实 → M3 别用,留作后续。
- **成本**:embeddings 用百炼 v4(answer_relevancy 才需,且每样本只 embed 几条反推问题,量小);判官用 GLM-5.2。都走已打通的同一个 `DASHSCOPE_API_KEY`。

### 安装期风险(交 dev 装时留意)【推测】
- ragas 对 langchain 全系 **unpinned** → pip 拉最新 langchain-openai;项目是 langchain **1.x**,理论兼容但**装完务必 `python -c "import ragas; from langchain_openai import ChatOpenAI"` 冒烟**,确认没把 langchain 降级/冲突。
- `datasets>=4.0.0` 重(pyarrow);若只用 `from_list` 不碰 HF Dataset,它仍是 ragas 硬依赖躲不掉,接受即可。

## 5. 黄金集 schema 建议(JSONL,一行一题)

```jsonc
{
  "id": "q001",
  "question": "NCCL 在分布式训练里解决什么问题?",   // → user_input(必填)
  "reference": "NCCL 提供多 GPU/多机集合通信原语……",   // → reference(context_recall/precision 必需;faithfulness/answer_relevancy 不需)
  "relevant_doc_ids": ["AI_Infra/xxx", "..."],          // 自算 Hit@k/MRR 用;= chunk metadata 的 doc_id 源文档粒度
  "category": "AI_Infra",                                // 分区(blog/AI_Infra),分层看分
  "expected_mode": "grounded"                            // grounded|general|refuse:测双模式闸门(接地/通用/弃答)
}
```
运行期由 pipeline 现填、**不入黄金集**的:`response`(生成答案)、`retrieved_contexts`(检索块文本)。
可选:`reference_contexts`(若要 NonLLM/ID-based 检索精度)。

**要点**:
- **每条都写 `reference`**——否则丢掉 context_precision + context_recall 两项。
- `relevant_doc_ids` 与 `reference` 是两码事:前者给检索排序指标(客观 id 命中),后者给 RAGAS 语义指标。两者都要,黄金集才能同时覆盖"检索准不准(Hit@k/MRR)"和"答得好不好(faithfulness/relevancy/recall/precision)"。
- `expected_mode` 支持验 notes 里定的**三结局兜底阶梯**(接地/通用/弃答),库外问题(红烧肉)标 `general`/`refuse`。
