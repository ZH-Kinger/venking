> LLM=GLM-5.2（OpenAI 兼容端点），向量库 Chroma。
> 调研日期 2026-07-12。可信度标注：【文档】=官方/一手来源，【实测】=取证，【推测】=未证实。

## 主题一：LLM 网关 / 认知路由

### 1. 「LLM gateway」到底做什么

LLM 网关是坐在「你的应用」与「模型提供方」之间的一层，把多家模型统一成一个（通常 OpenAI 兼容）
API，并在这一层集中做可靠性、成本、安全治理。典型能力矩阵：

| 能力 | 说明 | 代表工具 |
|---|---|---|
| 模型路由 | 一个端点后面挂多模型，按规则/负载/成本选目标 | LiteLLM, Portkey |
| 失败回退 fallback | 主模型挂了/超时自动切备用（如 GLM 挂→切另一端点） | LiteLLM, Portkey（含熔断/条件路由） |
| 重试 retry | 指数退避重试瞬时错误 | LiteLLM, Portkey |
| 限流/预算 | 虚拟 key、预算上限、RPM/TPM 限速 | LiteLLM, Portkey |
| 成本追踪 | 按 key/模型统计 token 与花费 | LiteLLM, Portkey |
| 响应缓存 | LiteLLM=Redis 精确匹配缓存；Portkey=语义缓存（相似 query 命中） | LiteLLM, Portkey |
| 鉴权 | 虚拟 API key 管理，隔离真实 provider key | LiteLLM, Portkey |
| PII 脱敏/护栏 | 内容过滤、越狱检测、PII 红act（LiteLLM 无内建，需自写中间件） | Portkey |
| 可观测 | 每请求延迟/token/成本/缓存命中日志面板 | Portkey（开箱更强） |

【文档】来源：
- Portkey vs LiteLLM: https://www.truefoundry.com/blog/portkey-vs-litellm
- LLM Gateways Compared 2026: https://wavect.io/blog/llm-gateway-router-comparison-2026/
- The LLM Gateway Playbook Part 3: https://medium.com/@adnanmasood/portkey-vs-litellm-routing-fallbacks-cost-tracking-and-control-the-llm-gateway-playbook-part-195855dc25c3

要点：
- **LiteLLM**：开源自托管主力。YAML 配路由/回退/负载均衡（round-robin、least-latency、
  cost-optimized）。缓存是 **Redis 精确匹配**。无内建护栏/PII/prompt 版本/A-B。代理约加 10-20ms 开销
  （相对 LLM 本身 500ms-5s 可忽略）。
- **Portkey**：企业级，观测 + 护栏 + 语义缓存更强；2026-03 起网关核心已开源(Apache 2.0)可自托管。

### 2. 关键区分：认知/语义路由器 vs 基础设施网关（架构上是两回事）

这两个词经常被混为一谈，但它们在架构上是**不同层、不同目的**：

**A. 基础设施网关（infra gateway）** —— LiteLLM / Portkey
- 目的：**可靠性、成本、鉴权、缓存**。它不关心 query 的语义。
- 位置：应用之外的一层代理（或 SDK 包装），对每个请求做「运维治理」。
- 决策依据：provider 健康度、延迟、成本、限额、key —— 都是**运维信号**。

**B. 认知/语义路由器（cognitive / semantic router）** —— semantic-router / RouteLLM
- 目的：**为每个 query 选走哪条路径/哪个模型/哪个 prompt/要不要开推理**。它读的是 query 的**语义/意图**。
- 位置：**应用逻辑内部**（在 agent 的图里、在编排层），是业务决策的一部分。
- 决策依据：query 的**含义**（embedding 相似度）或 query 的**难度**（学习到的分类器）。

两者子类型再细分：

| | RouteLLM | semantic-router (aurelio-labs) | vLLM Semantic Router |
|---|---|---|---|
| 问的问题 | 「这题够难，值得用贵模型吗？」 | 「这 query 意图属于哪条 route（prompt/工具/话题）？」 | 「意图是什么？要不要开 CoT 推理？」 |
| 机制 | 在人类偏好数据上训练的**二分类器**，强/弱模型二选一 | 定义 `Route`+示例 utterances，query embedding 与之比余弦相似度 | embedding + 意图分类 + 安全/幻觉检测 |
| 决策层 | **模型选择**（成本-质量权衡） | **动作/路径选择**（prompt/工具/话题守卫），**非选模型** | 请求级 Mixture-of-Models |
| 许可 | Apache 2.0（UC Berkeley/Anyscale/Canva, ICLR 2025） | MIT | Apache 2.0 |

【文档】来源：
- RouteLLM vs vLLM Semantic Router: https://www.gingerlabs.ai/blog/routellm-vs-vllm-semantic-router
- vLLM Semantic Router 论文: https://arxiv.org/html/2510.08731v1
- semantic-router (aurelio-labs): https://github.com/aurelio-labs/semantic-router

**核心澄清**：
- 「基础设施网关」= 把请求**可靠、便宜、安全**地送出去（运维层，与语义无关）。
- 「认知/语义路由」= 决定这个 query 该走**哪条业务路径/哪个模型**（应用层，纯看语义/难度）。
- 「语义路由 semantic routing」是一种**技术**（用 embedding 向量搜索做决策，快）；
  「模型路由 model routing」是一个**目标**（在模型池里选谁）。RouteLLM 是模型路由的典型；
  aurelio 的 semantic-router 主要是「路由到 prompt/工具/话题」而**不是选模型**。
- 「路由器延迟悖论」：路由器本身必须极低延迟，否则它增加的延迟抵消了它省的时间；
  因此 embedding 向量搜索（毫秒级）优于「用一个 LLM 来决定路由」（又慢又贵）。
  来源：https://arxiv.org/html/2510.08731v1

### 3. 对单用户个人项目的右尺寸建议

单用户 = 没有多租户、没有并发洪峰、没有跨团队成本分摊、没有对外鉴权边界。
逐项裁剪：

| 能力 | 单用户是否必要 | 建议 |
|---|---|---|
| 模型路由（多模型） | 视需求 | 若只有 GLM-5.2 一个模型，**不需要**路由器；若将来加一个便宜模型做粗筛，再上 |
| 失败回退 fallback | **有价值** | GLM 端点偶发 5xx/超时值得兜底。但**不必起独立网关**——用 LangChain 的 `with_fallbacks()` / `with_retry()` 或 tenacity 在代码里做即可 |
| 重试 retry | **必要** | 同上，代码级（tenacity / LangChain `.with_retry`）足够 |
| 限流/预算 | **不必要** | 单用户自己就是限流器。GLM 侧的账户配额已够 |
| 成本追踪 | 轻量有用 | 用 LangSmith/回调记 token 即可，不需要网关的多 key 计费 |
| 响应缓存 | **可选** | 精确缓存对固定 query 有用；RAG 场景 query 多变，语义缓存对「极致精准」反而有风险（近似命中可能返回旧答案）。**默认关，需要再开** |
| 鉴权 | **不必要** | 无对外暴露、无多 key。key 放环境变量即可 |
| PII 脱敏/护栏 | 视数据 | 单用户自己的数据，通常不需要 |
| 认知/语义路由 | 视架构 | 若图里有「简单 query 直答 vs 复杂 query 走完整 RAG」的分叉，这是**认知路由**，但可在 LangGraph 里用**条件边 + 一个轻量分类节点**实现，不需要引第三方路由服务 |

**明确反模式（避免过度工程）**：
- **不要**为单用户起独立的 LiteLLM/Portkey 网关服务（多一个进程、多一层故障、多运维）。
- **不要**为缓存起 Redis 集群；真要精确缓存，用本地 SQLite/内存字典即可。
- **不要**引 RouteLLM/semantic-router 这类独立服务，除非确实有多模型或多路径的语义分叉需求。

**正当理由才上网关**（本项目大概率不满足）：需要跨多个真·独立模型做回退/负载均衡、需要对多个下游
应用统一鉴权、需要企业级审计/合规。

## 主题二：LangGraph 里的记忆（已核对 1.x API）

> LangGraph 1.x 文档已并入 `docs.langchain.com/oss/python/langgraph/*`。以下 API 名均按 1.x 核对。

### 1. 短时记忆：Checkpointer（thread 级）

- **概念**【文档】：checkpointer 把「一个 thread 的图 state」按快照(checkpoint)持久化，用于会话续接、
  human-in-the-loop、time-travel、故障恢复。
- **thread_id 语义**【文档】：thread 是一串 checkpoint 的唯一 ID。调用时经 config 传：
  `{"configurable": {"thread_id": "1"}}`。缺 thread_id 会报
  `ValueError("Checkpointer requires one or more of the following 'configurable' keys: [...]")`。
  同一 thread_id 续接对话；换 thread_id = 全新对话。若带 `checkpoint_id` 则取该具体快照，否则取该 thread 最新快照。
- **内存版（开发）**【文档】：
  ```python
  from langgraph.checkpoint.memory import InMemorySaver   # 1.x 官方示例用这个名字
  checkpointer = InMemorySaver()
  graph = builder.compile(checkpointer=checkpointer)
  ```
  ⚠️ **API 漂移点**：老代码/教程里的 `MemorySaver` 与 `InMemorySaver` 同在
  `langgraph.checkpoint.memory`。1.x 官方文档一律用 **`InMemorySaver`**；`MemorySaver` 仍作为向后兼容别名存在。
  【文档】InMemorySaver 见 add-memory / persistence 页；【推测】MemorySaver 为别名（未在 1.x 文档正面确认，建议以 `InMemorySaver` 为准）。
- **SQLite 版（本地持久化，适合单用户生产）**【文档】：
  独立包 `langgraph-checkpoint-sqlite`。
  ```python
  from langgraph.checkpoint.sqlite import SqliteSaver
  with SqliteSaver.from_conn_string("checkpoints.sqlite") as checkpointer:
      graph = builder.compile(checkpointer=checkpointer)
  # 异步：from langgraph.checkpoint.sqlite.aio import AsyncSqliteSaver
  ```
  ⚠️ SqliteSaver 为轻量同步用途、不适合高并发多线程；异步用 `AsyncSqliteSaver`。
  生产多并发才需 `PostgresSaver`（`from langgraph.checkpoint.postgres import PostgresSaver` + `.setup()`）。
- **接口**【文档】：所有 checkpointer 实现 `BaseCheckpointSaver`：`.put/.put_writes/.get_tuple/.list/
  .delete_thread()`；异步图需 `.aput/.aget_tuple/...`。
- **安全**【文档】：默认序列化器 `JsonPlusSerializer` 允许任意 Python 类型；新应用建议设环境变量
  `LANGGRAPH_STRICT_MSGPACK=true` 或传 `allowed_msgpack_modules` 限制反序列化类型。

来源：
- Persistence: https://docs.langchain.com/oss/python/langgraph/persistence
- Add memory: https://docs.langchain.com/oss/python/langgraph/add-memory
- Checkpoints 参考: https://reference.langchain.com/python/langgraph/checkpoints
- SqliteSaver 参考: https://reference.langchain.com/python/langgraph.checkpoint.sqlite/SqliteSaver
- langgraph-checkpoint-sqlite PyPI: https://pypi.org/project/langgraph-checkpoint-sqlite/

### 2. 长时记忆（跨会话）：Store API

- **概念**【文档】：Store 存「图 state 之外」的应用级数据，用于**跨 thread**的长期记忆
  （用户偏好、事实、共享知识）。金句：没 checkpointer 每次 invoke 都是新对话；没 Store 每个新 thread 都是新关系。
- **命名空间/键值**【文档】：数据按 namespace（元组，如 `(user_id, "memories")`）组织，key 是记忆 ID，value 是 JSON。
  ```python
  from langgraph.store.memory import InMemoryStore
  store = InMemoryStore()
  store.put(("user_123", "memories"), "1", {"text": "I love pizza"})   # put(namespace, key, value)
  store.search(("user_123", "memories"), query="I'm hungry", limit=1)   # search(namespace, query=, limit=)
  # 异步：aput / asearch
  ```
- **语义检索**【文档】：InMemoryStore 支持 `index` 参数挂 embedding 做向量检索：
  ```python
  store = InMemoryStore(index={"embed": embeddings, "dims": 1536, "fields": ["memory"]})
  ```
- **节点里怎么拿 store**（⚠️ 主要 API 漂移点）【文档】：
  1. **推荐**：Runtime 对象 —— `async def node(state, runtime: Runtime[Context]): runtime.store.asearch(...)`
  2. **兼容**：按参数名注入 —— `def node(state, config: RunnableConfig, *, store: BaseStore):`
     （keyword-only、类型注解 `BaseStore`，LangGraph 自动注入）
  旧教程可能出现的 `get_store()` 访问器在当前 add-memory 文档**未出现**，建议用上面两种。
- **编译时同时挂两者**【文档】：
  ```python
  graph = builder.compile(checkpointer=checkpointer, store=store)
  # 调用时 thread_id 走 short-term，user_id 走 long-term scoping
  ```
- **生产后端**：`InMemoryStore` 仅开发用（进程退出即丢）；生产换 `PostgresStore.from_conn_string(...)`，
  或本地 SqliteStore。也可接 Chroma/Pinecone/Weaviate 作向量后端，接口 put/get/search 一致。
  ⚠️ Store 只是**原语**（带可选向量索引的 KV 命名空间）；实体抽取、召回、矛盾消解要自己写。

来源：
- Persistence: https://docs.langchain.com/oss/python/langgraph/persistence
- Add memory: https://docs.langchain.com/oss/python/langgraph/add-memory

### 3. State（TypedDict + reducer）作为「黑板/状态总线」

【文档】来源：https://docs.langchain.com/oss/python/langgraph/graph-api

- State = **schema + reducer**。schema 是所有节点/边的输入输出契约；reducer 决定「节点返回的更新如何并进累积 state」。
- **默认 reducer**：直接覆盖（新值替换旧值）。
  ```python
  from typing_extensions import TypedDict
  class State(TypedDict):
      foo: int
      bar: list[str]
  ```
- **自定义 reducer（用 Annotated）**：让某字段**累加**而非覆盖 —— 这就是多节点「往黑板上追加中间产物」的机制。
  ```python
  from operator import add
  from typing import Annotated
  class State(TypedDict):
      foo: int
      bar: Annotated[list[str], add]   # bar 追加，foo 覆盖
  ```
  reducer 是二元函数：左参=累积 state，右参=最新节点更新。
- **消息专用 reducer `add_messages`**：既追加又能按 ID 更新已有消息，还把 dict 形式消息反序列化为 LangChain 对象。
  ```python
  from langchain.messages import AnyMessage
  from langgraph.graph.message import add_messages
  from typing import Annotated
  class GraphState(TypedDict):
      messages: Annotated[list[AnyMessage], add_messages]
  ```
  或直接子类化 `MessagesState`：
  ```python
  from langgraph.graph import MessagesState
  class State(MessagesState):
      documents: list[str]
  ```
- **黑板/总线用法**：各节点（检索、重排、生成、校验）把中间产物写进各自 state 字段；
  用 `Annotated[list, add]` 的字段可让多个并行节点的产出自动**合并**（如多路检索结果汇聚），
  这正是「状态总线」——节点间不直接互相调用，只读写共享 State。
- **1.x import 路径**【文档】：
  ```python
  from langgraph.graph import StateGraph, START, END, MessagesState
  from langgraph.graph.message import add_messages
  builder = StateGraph(State)          # 可选 input_schema=..., output_schema=...
  graph = builder.compile()
  ```

### 4. 对本项目（单用户 RAG）的记忆右尺寸建议

| 机制 | 建议 | 理由 |
|---|---|---|
| Checkpointer | **用 `SqliteSaver`**（本地文件） | 单用户生产：要跨进程重启续接对话、要故障恢复。SQLite 无需服务、零运维、够用。开发期可先 `InMemorySaver` |
| thread_id | **一个会话一个 thread_id** | 单用户仍可有多个独立会话线。用户级偏好不要塞进 thread |
| Store 长时记忆 | **按需，先别过度** | 若需要「跨会话记住用户偏好/长期事实」再上。初期可只用 `InMemoryStore`，稳定后换 SqliteStore/Postgres。⚠️ 注意别把「文档知识库」和「用户记忆」混淆——文档知识走 Chroma RAG，用户记忆才走 Store |
| Store 后端别重复 | **复用已有 Chroma** | 你已有 Chroma。长期记忆若要语义检索，可直接用 Chroma 存记忆命名空间，不必再引第二套向量库 |
| State/reducer | **核心，重点设计** | 这是 RAG 图的骨架。为检索结果、重排分数、引用、校验反馈等设计清晰字段；并行检索用 `Annotated[list, add]` 汇聚 |
| PostgresSaver/Store | **不必要** | 无并发，SQLite 足矣。除非将来多用户/高并发 |
| 序列化安全 | **建议开** | 生产项目设 `LANGGRAPH_STRICT_MSGPACK=true`，限制反序列化类型 |

## 针对本项目的落地建议（总）

1. **不要起独立 LLM 网关服务。** 单用户 + 单模型(GLM-5.2)场景，网关的多租户/鉴权/限流/成本分摊价值都用不上。
   把「可靠性」需求下沉到代码：用 LangChain 的 `.with_retry()` / `.with_fallbacks()`（或 tenacity）
   给 GLM 调用加重试与（若有备用端点）回退即可。**不起 Redis 集群**。

2. **缓存默认关。** RAG + 「极致精准」目标下，语义缓存的近似命中会带来错误答案风险；真要缓存用本地精确缓存
   （SQLite/dict），只对确定可复用的调用开。

3. **「认知路由」如有需要，用 LangGraph 条件边实现，不引第三方。** 若要「简单 query 直答 vs 复杂走完整 RAG」
   的分叉，用一个轻量分类节点 + `add_conditional_edges` 即可，不必引 RouteLLM/semantic-router 服务。
   记住区分：这属于**应用层认知路由**，与运维网关是两回事。

4. **记忆分层落地**：
   - 短时：开发 `InMemorySaver` → 生产 `SqliteSaver`（本地文件），一会话一 thread_id。
   - 长时：**按需**上 Store；用户记忆与文档知识库分开（知识走 Chroma RAG，记忆走 Store，可复用 Chroma 后端）。
   - State：作为图的黑板/总线重点设计，检索类中间产物用 `Annotated[list, add]` reducer 汇聚。
   - 生产设 `LANGGRAPH_STRICT_MSGPACK=true`。

5. **API 漂移提醒（1.x）**：checkpointer 内存类用 `InMemorySaver`（非旧名 `MemorySaver`）；
   节点内访问 Store 用 `runtime.store` 或 `store: BaseStore` 参数注入（旧 `get_store()` 已不在当前文档）；
   import 走 `langgraph.graph` / `langgraph.checkpoint.*` / `langgraph.store.*`。落地前请以
   `docs.langchain.com/oss/python/langgraph/*` 为准二次核对。
