# 知识库存储规范(KB Storage Spec)

> 目的:让知识库的**增 / 改 / 删 / 重建 / 同步**干净、幂等、可追溯。
> 铁律:**源文档是唯一事实源,向量库是它的派生物**;任何时候都能从源重建,且能精确定位到某文档的所有 chunk。

---

## 1. 目录约定(统一两区,各一个根)

**区 A — RAG/管道工作区**(gitignore,唯一根 `rag-server/data/`):
```
rag-server/data/
├─ inbox/<分类>/                 # ★唯一投放入口:原始源(lakebook/pdf/md/图),按扩展名分派
├─ chroma_db/                    # Chroma 向量库(持久化)
├─ manifest.json                 # 知识库清单(每源文档一条)+ 顶层 index_version 版本闸
├─ record_manager.sqlite         # LangChain SQLRecordManager(增改删同步)
├─ convert_state.json            # convert 管道幂等状态(输入 sha256)
├─ pdf_images/  caption_cache/   # PDF 多模态派生(原图 / VL caption 缓存,按需)
├─ feedback/                     # 反馈数据(M3)
└─ _archive/                     # 被取代/留存不处理的原件(如已改用 lakebook 的 PDF 版)
```
**区 B — 博客发布区**(git 跟踪,VuePress 强制位置,**不可移**):
```
src/posts/<分类>/                # 转换出的文章(嵌套目录 = 源层级;容器→README.md,叶子→.md)
src/.vuepress/public/assets/<分类>/  # 图片(语雀源图已是 cdn URL,无需拷)
```

**数据流**:`inbox/<分类>/源文件` --scripts/convert.py(按扩展名)--> `src/posts/<分类>/*.md`
--(blog_md loader)--> RAG。一份原始源 → 一处文章 → 自动入库,**不重复**。

**源文档事实源**:博客 md(含转换出的 AI_Infra)= `../src/posts/**/*.md`;RAG-only 源在
`sources.toml` 登记 path+type。原始投放件留在 `inbox/`(gitignore),PDF 冗余原件归 `_archive/`。

## 2. 稳定标识(ID)约定 —— 幂等与精确删除的基石

| 概念 | 规则 | 例子 |
|---|---|---|
| `doc_id` | 源文档稳定唯一 ID = **相对路径**(人读+稳定) | `AI_LLM/RAG.md` / `pdf/AI_INFRA_SRE` |
| `chunk_id` | `"{doc_id}::{chunk_index}"`(确定性) | `AI_LLM/RAG.md::3` |
| `content_hash` | chunk 正文 sha256 → 检测该块是否变 | `ab12ef…` |
| `doc_hash` | 源文档全文 sha256 → 检测整篇是否变 | `9f3c…` |

**为什么**:确定性 `chunk_id` → 重复入库是 **upsert 覆盖**(不产生重复);统一 `doc_id` → 删/改一篇文档时能 `where={"doc_id": ...}` **一次性清掉它的所有 chunk**。

## 3. 规范化 metadata schema(每个 chunk 必带)

```jsonc
{
  "doc_id":        "AI_LLM/RAG.md",         // 源文档稳定ID(删改按它)
  "chunk_id":      "AI_LLM/RAG.md::3",
  "source":        "RAG.md",                // 文件名(展示/引用)
  "source_type":   "blog_md",               // blog_md | pdf_text | pdf_image
  "category":      "AI大模型",
  "title":         "RAG",
  "page":          42,                       // 仅 PDF
  "section":       "NCCL",                    // 仅 PDF(字号识别)
  "image_path":    "data/pdf_images/p42_1.png", // 仅图caption
  "content_hash":  "ab12…",
  "doc_hash":      "9f3c…",
  "ingested_at":   "2026-07-12",
  "index_version": "temb-v4|1024|md-header|cs500"  // 见 §5
}
```
> 引用定位、self-query 过滤、按来源删除,全靠这套 metadata。**第一天就固定,别事后补。**

## 4. KB 生命周期操作(`kb.py` CLI)

| 命令 | 语义 | 实现要点 |
|---|---|---|
| `kb sync` | 扫源 ↔ manifest 对账,自动增/改/删 | 见下方对账算法(核心) |
| `kb add <path>` | 入单个文档 | 计算 doc_hash → 分块 → upsert → 记 manifest |
| `kb update <doc_id>` | 重新入某文档 | **先 `delete(where={doc_id})` 清旧,再 add** |
| `kb delete <doc_id>` | 删某文档全部 chunk | `delete(where={"doc_id": doc_id})` + manifest 删条目 + 清其缓存图 |
| `kb status` | 列 KB 内容+统计 | 读 manifest:文档数/chunk数/各 source_type |
| `kb rebuild` | index_version 变了→全量重建 | 清 chroma_db → 全量重入 |

**`kb sync` 对账算法(幂等增量同步)**:
```
扫描所有源文档 → 算每篇 doc_hash
对每篇:
  - manifest 无此 doc_id            → 新增:分块+入库+登记
  - manifest 有但 doc_hash 变了      → 更新:按 doc_id 删旧 chunk + 重新入库 + 更新登记
  - manifest 有且 hash 未变          → 跳过(省钱省时)
manifest 里有、但磁盘已不存在的 doc  → 删除:按 doc_id 清 chunk + 删登记 + 清缓存
```

## 5. 索引版本 `index_version` —— 防"坐标系错乱"

指纹 = `embedding模型 | 维度 | 分块策略 | chunk_size`,如 `temb-v4|1024|md-header|cs500`。
- 写进每个 chunk 的 metadata,并存一份到 manifest 顶层。
- **任一项改变(换 embedding / 改维度 / 改分块)→ 旧向量全部作废**(不同模型坐标系不可混用,researcher 标注的"模型一致性致命坑")。启动时校验 manifest 的 index_version 与当前 config 是否一致,不一致就提示 `kb rebuild`。

## 6. 实现方案(已核实)—— 混合:Indexing API 管同步 + manifest 管版本闸

**最终决定(researcher 取证)**:**LangChain Indexing API + `SQLRecordManager` 管日常增/改/删/同步**(自动 hash 去重、跳过未变、按 source 删旧,工业验证、Chroma 官方支持),**外加一个薄 manifest.json 只管"模型/维度/分块版本闸"**(Indexing API 按 doc hash 追踪,**察觉不到 embedding 模型变化**,这个坑得自己守)。约 30 行搞定版本闸,其余交给轮子——最省心又不失学习点。

**日常同步(核心一行)**:
```python
from langchain.indexes import SQLRecordManager, index
from langchain_chroma import Chroma

vs = Chroma(collection_name="kb", embedding_function=emb, persist_directory=str(settings.chroma_dir))
rm = SQLRecordManager("chroma/kb", db_url=f"sqlite:///{settings.record_manager_path}")
rm.create_schema()  # 首次

# 全量对账(能自动 purge 磁盘已删的文档):传入全部 docs
index(all_docs, rm, vs, cleanup="full", source_id_key="doc_id")
#   cleanup="incremental" → 只清"这次传入的 source 的旧版本",不 purge 未传入的
```
- `source_id_key="doc_id"` = 让它按源文档分组,改一篇→自动删该 doc 旧 chunk 再写新。
- 返回 `{num_added, num_updated, num_skipped, num_deleted}` —— 天然的入库报告。
- 清空:`index([], rm, vs, cleanup="full", source_id_key="doc_id")`。

**Chroma 删除(已核实)**:
- `vs.delete(ids=[...])` **只支持 id**,wrapper **不吃 where**。
- 按 metadata 删一篇的所有块,两种:
  ```python
  ids = vs.get(where={"doc_id": X})["ids"]; vs.delete(ids=ids)   # 稳,推荐
  vs._collection.delete(where={"doc_id": X})                     # 一行,直连底层
  ```
  where 操作符:`$eq/$ne/$gt/$gte/$lt/$lte/$in/$nin/$and/$or/$contains`;`where_document={"$contains": "..."}` 按正文过滤。

**kb.py 命令 → 实现映射**:
| 命令 | 实现 |
|---|---|
| `kb sync` | `index(全部docs, rm, vs, cleanup="full", source_id_key="doc_id")` |
| `kb add/update <doc>` | `index(该doc的chunks, rm, vs, cleanup="incremental", source_id_key="doc_id")` |
| `kb delete <doc_id>` | 从源移除后跑 `kb sync`(managed 干净);或临时 `vs.get(where)+delete` |
| `kb status` | 读 manifest + `vs._collection.count()` |
| `kb rebuild` | 版本闸不匹配 → 清 collection+record_manager → `cleanup="full"` 全量重建 |

**版本闸(manifest.json,~30 行,自己守)**:顶层记 `{embedding_model, embedding_dim, chunking, index_version}`;**启动时**比对 config 的 `index_version`,不一致就**拦住检索**并提示 `kb rebuild`——防"拿 A 模型向量查 B 模型索引"这个头号静默杀手。

> ⚠️ 别把 Indexing API 指向"在它之外预先塞过数据的 collection"(record manager 不认那些行)。所以要么全程用它管,要么 rebuild 一次交给它接管。

## 7. 与其他模块的接口
- **M1 ingest** 按本规范写 metadata,交 `index()` 入库,维护 manifest 版本闸。
- **M3 评测** 的 `source_doc_id` 直接复用 `doc_id`,分离检索失败 vs 生成失败。
- **引用** 用 `doc_id`/`source`/`page` 定位。
- **self-query** 按 `category`/`source_type`/`page` 过滤。
- **反馈闭环** 记录命中的 `chunk_id`,便于定位坏块。
