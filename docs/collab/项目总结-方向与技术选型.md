# 项目总结:方向 · 选择原因 · 实现难度 · 方案对比

> 生产级、极致精准、全能的 **Agentic RAG 对话 Agent**(over 个人博客 ZH-Kinger)。
> 本文把 9 路调研 + 逐步决策沉淀成技术选型依据。难度标注:⭐低 / ⭐⭐中 / ⭐⭐⭐高。

---

## 一、一句话定位与整体方向

**给自己的博客(205 篇 md + 1 份 333 页 infra PDF)做一个会思考、带引用、无据弃答的问答 agent,同时能写代码/画流程图/闲聊。**

**数据流(端到端方向)**:
```
异构语料(md+PDF图文) ──入库──> 向量库(Chroma, 带 metadata)
                                      │
用户问题 → [路由] ── rag 分支 ──> 混合检索→重排→打分→(改写/联网兜底)→生成带引用→护栏(弃答)
              └──── general 分支 ──> 代码/流程图/闲聊(不接地、不带引用)
                                      │
                          Gradio 对话界面(流式/复制/👍👎/简短·详细/Mermaid)
                                      │
                          反馈闭环(👍👎→Langfuse→评测黄金集/few-shot)
                          评测(RAGAS+检索指标)贯穿每次改动
```

**核心哲学**:精准 > 速度;**宁可有据或说"不知道",绝不臆造**;入库质量是精准天花板;精准与"全能"用**双模式路由**隔离,互不污染。

## 二、关键技术选型:方向 / 选择原因 / 难度 / 方案对比

### 1. 对话大模型 —— GLM-5.2(OpenAI 兼容接口) ⭐
- **为什么**:用户指定;通过 OpenAI 兼容端点,官方 `openai` SDK 直接调,换 base_url 即可,零胶水。
- **对比**:Qwen / DeepSeek / 本地 Ollama —— 同样兼容,换 base_url+模型名即可,架构不锁死。
- **注意**:GLM-5.2 是**对话模型**,只能干"语言/推理"活(生成、打分、路由、改写、LLM 重排、看图若多模态)。**不能做 embedding**。

### 2. 向量化 Embedding —— 百炼 text-embedding-v4 ⭐⭐
- **为什么**:OpenAI 兼容、1024 维、免费 100 万 token/90 天、中文质量好;**不能用 GLM-5.2**(对话模型做不了向量化,是另一类模型)。
- **对比**:

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **text-embedding-v4(云)** | 免 torch、质量好、免费额度够 | 联网、按量计费 | ✅ **选它** |
| 本地 text2vec | 离线、免费、贴合用户笔记 | 依赖 torch(本机 Py3.14 实测可装但重) | 二期离线对比 |
| GLM-5.2 做 embedding | —— | **架构上不可能** | ✗ |

- **坑**:`OpenAIEmbeddings` 默认 batch 1000 > 百炼上限 10 → 必须 `chunk_size=10, check_embedding_ctx_length=False`。

### 3. 向量库 —— Chroma ⭐
- **为什么**:轻量、本地持久化、支持 metadata 过滤(self-query 需要)、LangChain 一等支持。
- **对比**:FAISS(纯索引无 metadata 便利)/ Milvus·Qdrant(生产强但重,单机学习过度)。→ Chroma 甜点。

### 4. PDF 解析 —— PyMuPDF(裸 fitz) ⭐⭐⭐
- **为什么**:唯一"快 + 能抽图 + 保留页码/字号/坐标"三合一;能在切块前清 `\x00` 脏字符;**无书签时靠字号识别标题重建章节**。
- **对比**:

| 方案 | 抽文字 | 抽图 | 结构/页码 | 结论 |
|---|---|---|---|---|
| **PyMuPDF(fitz)** | ✅ | ✅ | ✅ 字号/页码 | ✅ **选它** |
| PyPDFLoader | ✅ | 靠OCR | 弱 | ✗ |
| PDFPlumber | ✅ 表格强 | ❌ | 中 | ✗ |
| Unstructured | ✅ 切分细 | ✅ | ✅ | 依赖重、OCR慢,过度 |

- **难点**:333 页、62 图、无书签、有脏字符 → 结构化分块 + 图文分治,是全项目最难的入库环节。

### 5. 多模态图片处理 —— B(Qwen/GLM-VL captioning)+ D(命中带原图) ⭐⭐⭐
- **为什么**:把"多模态"降维成已掌握的文本 RAG;caption 带页面上下文更准;**caption 落盘缓存只付一次**;检索命中带出原图。
- **对比**:

| 路线 | 做法 | 效果 | 落地成本 | 结论 |
|---|---|---|---|---|
| A 丢弃 | 只索引文字 | 丢图信息 | 最低 | 应急 baseline |
| **B 视觉描述** | VL 把图→中文入库 | 好、同栈 | 中(62次调用<1元) | ✅ **主选** |
| C 多模态embedding | 图文同空间 | 检索最优(+32%MAP) | 高(需torch/独立collection) | 跳过 |
| **D 图文分离** | 命中带出原图 | 保留原图 | 低 | ✅ **叠加** |

### 6. 检索质量三件套 —— 混合检索 + 上下文检索 + 重排 ⭐⭐
- **方向**:堆准确率,且大多在**离线/检索期**完成,不牺牲运行时速度。

| 技术 | 治什么病 | 难度 | 为什么做 |
|---|---|---|---|
| **混合检索 BM25+RRF** | dense 对 `BF16`/`NCCL` 精确术语失灵 | ⭐⭐ | 最高 ROI,小语料上 BM25 更有效 |
| **上下文检索(Anthropic)** | chunk 断章取义 | ⭐⭐ | 小语料一次性索引成本几块钱,收益最大 |
| **重排 → 改用 GLM-5.2 做 LLM 重排** | 向量粗排不够精 | ⭐⭐ | 提精确率;用户要"全用GLM",故不引 gte-rerank |
| 父文档/small-to-big | 命中精确但上下文不足 | ⭐ | 便宜好学,博客分节天然契合 |
| self-query | 按分类/日期/博客↔PDF 精确过滤 | ⭐⭐ | 利于双语料路由 |

- **重排方案对比**:cross-encoder(bge/jina,需torch,最准)vs gte-rerank API(免torch)vs **LLM 重排(GLM-5.2,遵"全GLM",略慢但同模型)**。→ 遵用户意愿选 LLM 重排,gte-rerank 留作可选替代。

### 7. Agentic 框架 —— LangGraph 显式工作流(pattern B) ⭐⭐⭐
- **为什么**:状态图把"路由/打分/改写/兜底/生成/护栏"每个能力显式成节点,好调试、好教学、好加防死循环;比"检索器当工具"的 pattern A 更可控。
- **对比**:手写 ReAct 循环(最透明但样板多)/ LangChain AgentExecutor(黑盒)/ **LangGraph(工业标准+可视状态)**。
- **难点**:State 设计、条件边、两层防死循环(loop_step+max_retries / recursion_limit)、引用透传。

### 8. Agentic 方法学 —— 借思想不照搬 ⭐⭐

| 论文/方法 | 借什么 | 是否实现 |
|---|---|---|
| **ReAct** | Thought→Action→Observation 骨架 | ✅ 骨架 |
| **CRAG** | 打分检索→不行就兜底(联网/弃答) | ✅ 轻量版 |
| **Self-RAG** | 相关性/支持度自评 | ✅ 当打分节点(不训练) |
| **Adaptive-RAG** | 不检索/检索一次/迭代 的路由 | ✅ 融进 route_question |
| HyDE | 假设文档提召回 | 选做实验 |
| 多查询/RAG-Fusion | 多变体融合 | 跳过(和 rewrite 重叠) |

### 9. 工具设计 —— 少而精 4 工具 ⭐⭐
- **为什么**:工具从 4→51,选对率 43%→2%;GLM 类开源模型退化更快。软上限 ~10-20,**越少越稳**。
- **工具集**:`search_blog(query,category?)` / `web_search`(CRAG兜底) / `get_full_post` / `list_categories`。
- **对比/跳过**:动态工具检索(RAG-MCP/Toolshed)、MCP、路由→子agent —— 都要 ~15-20 工具或多领域才值得,**现在是过度工程**。

### 10. 评测 —— RAGAS + 检索指标(评测驱动开发) ⭐⭐⭐
- **为什么**:没度量就谈不上"极致精准";每次改动量化对比才能真迭代。
- **对比**:

| 框架 | 定位 | 结论 |
|---|---|---|
| **RAGAS** | RAG 专用4指标、reference-free、Langfuse 原生集成 | ✅ **选它** |
| DeepEval | pytest/CI 断言式回归 | 有 CI 再加 |
| TruLens | 内联反馈函数 | 选做 |
| LangSmith | 深度 LangChain 集成 | ✗ 锁定+计费,Langfuse 已够 |

- **指标**:忠实度/上下文精确率·召回率/答案相关性 + Hit@k/MRR;黄金集 50-100 条,schema 带 `source_doc_id`(分离检索失败 vs 生成失败)。

### 11. 护栏 & 可观测 & 可靠性 ⭐⭐
- **护栏**:证据优先 prompt + 强制引用 + **低相似度弃答** + 逐条 faithfulness(抓"看着有引用其实源里没有")。
- **可观测**:**Langfuse**(开源自托管、RAGAS 原生)> Phoenix(评测优先)> LangSmith(锁定)。
- **可靠性**:temp=0 打分器、tenacity 退避重试、LangGraph RetryPolicy/TimeoutPolicy/error_handler、一个备用 provider。**跳过**:全断路器+多provider网关(单人过度)。

### 12. 人类反馈 —— 务实闭环,不做真 RLHF ⭐⭐

| 方案 | 可行性 | 结论 |
|---|---|---|
| 真 RLHF(奖励模型+PPO) | 需多模型+GPU+海量偏好数据 | ✗ 个人项目=永不 |
| DPO 微调 | 单卡可跑但需数千偏好对 | 攒够再说,先只静默记录 |
| **反馈闭环** | 👍👎+纠正→黄金集/few-shot/调prompt | ✅ **选它**(最高 ROI) |

### 13. 全能能力 —— 双模式 + 生成不执行 ⭐⭐
- **双模式路由**:博客问题→接地RAG(带引用);代码/画图/闲聊→通用模式(不接地、不带引用,不进精准指标)。
- **代码**:只**生成+高亮**,**不执行**(45% AI 代码过不了安全测试;真要跑用 E2B 微VM,绝不本地 exec)。
- **Mermaid**:生成 + **解析-自动修复循环** + 客户端渲染(小心全角标点)。

### 14. 对话 UI —— Gradio(纯 Python) ⭐⭐
- **为什么**:纯 Python、原生 mermaid/复制/👍👎/重生成/历史,聚焦 agent 而非前端。
- **对比**:

| 方案 | 语言 | 反馈 | Mermaid | LangGraph | 生产 | 结论 |
|---|---|---|---|---|---|---|
| **Gradio** | Python | 原生 | 原生(流式闪) | 手动 | 中 | ✅ **默认** |
| assistant-ui | React | 适配器 | Streamdown原生 | 最佳 | 高 | 天花板,但要写React |
| Open WebUI | 成品 | 原生+导出 | 原生 | OpenAI兼容包 | 高 | 快上生产,学不到UI |
| Streamlit/Chainlit | Python | 有 | 需插件/无 | 手动/finicky | 低-中 | ✗ |

- **升级路径**:将来把 agent 包成 FastAPI OpenAI 兼容端点 → 接 Open WebUI / 自建 React,UI 可换。

## 三、实现难度总览与风险

| 模块 | 难度 | 主要风险 |
|---|---|---|
| M0 环境/配置 | ⭐ | ✅ 已完成(smoke 通) |

| M3 评测/反馈 | ⭐⭐⭐ | 黄金集质量(人工)、Langfuse 自托管 |

**最大的三个硬骨头**:PDF 图文入库(M1)、Agentic 状态图+护栏(M5)、评测黄金集(M3)。

## 四、分阶段落地路线(增量,可随时停)

1. **最小精准闭环**:M0✅ → M1(仅 md)→ M2 → M3 → 能问答 + 能量化。
2. **上难度**:PDF 专项入库 → M5 Agentic 核心 + 双模式。
3. **产品化**:M4 工具 → M6 对话 UI + 反馈 → M7 生产化。
4. **选做**:M8 记忆、self-query、CoVe、DPO 数据积累。
