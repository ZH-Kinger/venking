# ADR-0016: UI 流式方案 —— LangGraph custom writer
- 状态: 已采纳
- 日期: 2026-07-14
- 相关模块: M6

## 背景(为什么要做这个决策)
M6 对话 UI 要"逐字出答案"。但 M5 图的生成节点走**裸 openai SDK**(`client.chat.completions.create`),token 增量只被 `_consume` 打到 stdout,`answer_graph` 又是阻塞 `.invoke()`——UI 拿不到增量。要选一条"从图内 LLM token → UI"的通道。

## 选项(≥2,每个一句话)
- A `stream_mode="messages"`:LangGraph 自动把节点内 **LangChain chat model** 的 token yield 出来。
- B `stream_mode="custom"` + `get_stream_writer()`(选中):节点内主动 `writer(token)` 发自定义事件,`graph.stream()` 收。
- C 重构生成层为 LangChain `ChatOpenAI`,再用 A。
- D 不用图流式,UI 侧对 `answer_graph` 做整段返回(无流式)。

## 优劣对比
| 方案 | 优 | 劣 |
|---|---|---|
| A messages | 零侵入、最"正统" | **当前拿不到 token**:我们节点是裸 openai SDK 非 LangChain runnable,messages 模式对它无效 |
| B custom writer(选中) | 与现有裸 openai 流最契合,改动最小(print 旁加一行 writer);可发结构化事件(token/来源/进度) | 需在 `_consume` 手动发、且要 guard 非流式上下文 |
| C 重构成 ChatOpenAI | 能用 A、更标准 | 动生成层伤面大、牵连 rerank/grader 一致性,ROI 低 |
| D 不流式 | 最简单 | 长答案要等十几秒白屏,体验差,违背"全能对话 UI"目标 |

## 结论(选了哪个)
选 **B**:`llm._consume` 每 token 经 `get_stream_writer()(...)` 发 `{"type":"token","text":..}`(从 **`langgraph.config`** 导入,非 `langgraph.types`);UI 侧 `get_graph().stream(init, cfg, stream_mode=["custom","values"])`——custom 收 token 增量、values 收每步全量 state(取末份的 mode/sources)。新增 `graph.stream_answer()` 生成器封装,末尾 yield 汇总 dict(契约同 answer_graph)。

**关键 guard**:`get_stream_writer()` 在非图流式上下文(CLI/eval)会抛错 → try/except 吞掉退化为纯 print。实测 CLI/eval 行为不变、188 测试零回归、UI 侧 NCCL 收到 19 个 token。

## 为什么不选替代
- 不选 A:节点非 LangChain 模型,messages 模式实测拿不到 token(Explore 2026-07-14 核实)。
- 不选 C:为流式重构整个生成层,伤面大、风险高,而 B 一行 writer 即达目的。
- 不选 D:白屏等待十几秒,体验不达标。

## 回溯条件(什么情况下该重估)
- 若将来把生成层统一迁到 LangChain `ChatOpenAI`(比如为接 `.with_retry`/Langfuse 追踪)→ 可切回 A messages 模式,删掉手动 writer。
- 若要多路(工具/子图)细粒度事件 → 扩 custom 事件类型(已预留 `{"type":..}` 结构)。
