# ADR-0009: 网关右尺寸 —— 不上独立网关/Redis
- 状态: 已采纳
- 日期: 2026-07-12
- 相关模块: M5 / M7

## 背景(为什么要做这个决策)
照 Claude Code 学"网关"能力(可靠性/回退/重试/缓存)。业界常上 LiteLLM/Portkey 独立网关 + Redis 缓存。但本项目是**单用户 + 单模型(GLM-5.2)**,需判断该上多重。

## 选项(≥2,每个一句话)
- **A 独立基础设施网关(LiteLLM/Portkey)+ Redis 缓存**:企业级治理。
- **B 代码级薄封装**:`.with_retry()`/`.with_fallbacks()` 或 tenacity + 备用 provider,缓存默认关。

## 优劣对比
| 方案 | 优 | 劣 |
|---|---|---|
| A 独立网关 + Redis | 多租户/多模型/统一鉴权/成本分摊/语义缓存 | 多一个进程 + 一层故障 + 运维;单用户这些价值全用不上;语义缓存对"极致精准"有返旧答案风险 |
| **B 代码级薄封装** | 零额外进程、零运维、够用 | 无企业级面板/多 key 计费(本项目不需要) |

## 结论(选了哪个)
选 **B:代码级薄封装,不起独立网关服务、不上 Redis**。可靠性下沉到代码(重试 + 若有备用端点则回退);**语义缓存默认关**(RAG 精准场景近似命中会返旧答案);认知路由用 LangGraph 条件边 + 轻量分类节点实现(见 ADR:路由形态),不引 RouteLLM/semantic-router。可观测留 Langfuse(M6 有流量再接)。

## 为什么不选替代
- **不选独立网关**:R4 明确"单用户 = 没有多租户/并发洪峰/跨团队成本分摊/对外鉴权边界",网关的模型路由/限流/预算/鉴权/多 key 计费价值全落空;起独立服务 = 多进程 + 多故障点 + 运维,是过度工程。正当理由(多真独立模型回退/多下游统一鉴权/企业审计)本项目均不满足。
- **不上 Redis**:无并发,真要精确缓存用本地 SQLite/dict 即可。
- **语义缓存不开**:近似命中返回旧答案与"极致精准"目标冲突。

## 回溯条件(什么情况下该重估)
转多用户/高并发;接入多个真·独立模型需负载均衡/回退;需企业级审计合规。
